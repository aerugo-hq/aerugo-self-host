# Knowledge Layer: v1 design and scope

Status: draft v1 · Owner: Rama · Updated: 2026-10-01 · Working name: `knowledge-layer` / `kl` (renaming later is a find-and-replace)

## 0. What this is

An open-source, permission-aware knowledge platform for companies. Teams connect their own sources. The platform keeps two representations of what the company knows: a curated canonical layer in Open Knowledge Format (OKF v0.2), reviewed through pull requests, and a broad evidence layer (hybrid lexical and vector retrieval) for the long tail. Every read, whether from the web app, the REST API, or MCP, goes through one policy decision point that enforces permissions mirrored from the source systems. It ships as self-hosted open source and as a managed SaaS, from the same artifact.

Positioning: OKF standardizes the format and explicitly leaves storage, serving, query infrastructure, and access control out of scope. This project is the open-source, permission-aware OKF server, with RAG for the long tail. The features other open-source tools gate behind paid editions (source permission sync, SSO, RBAC, audit, multi-tenancy) are core here.

## 1. Invariants

These are non-negotiable. They are enforced in code review, in `CLAUDE.md`, and in the release-gating test suite.

1. **One policy decision point.** Every read path filters by the caller's entitlements before ranking (inside the index query, via row-level security), then post-checks the final set against the authorization engine. No endpoint, tool, or job reads content around it.
2. **Scope is not permission.** Workspace selection and the org-wide toggle change where we look, never what a caller may see.
3. **Audience monotonicity.** A derived concept's audience is never wider than the narrowest audience among its sources.
4. **Secrets never touch Postgres, logs, traces, or Git.** The database stores references only.
5. **Every door carries the end user's identity.** No shared integration key that bypasses document ACLs.
6. **Egress follows the data.** Content goes to a model (generation or embeddings) only if that content's policy allows that endpoint.
7. **Deny by default.** Unknown principal, unknown ACL, stale ACL on restricted content, or missing request context means no access.
8. **Tenant data tables carry `org_id` and row-level security from the first migration.**
9. **Every new read surface ships with permission-leak tests** in the release-gating suite.
10. **No new infrastructure dependency without an ADR.** Every dependency is a tax on every self-hoster.

## 3. Architecture

### 3.1 Cells

A **cell** is one complete deployment: API, workers, MCP server, web app, Postgres, OpenFGA, object store, and secrets backend.

- **Self-hosted:** the customer runs one cell (Docker Compose for a single node, Helm for Kubernetes).
- **SaaS:** we run one cell per customer, in its own GCP project, in the region the customer picks.
- **Fleet control plane (ours, SaaS only):** provisions cells with Terraform, rolls upgrades through rings (internal cell, then a canary customer, then everyone), monitors health. It never holds customer content.

Why silo: it gives the strongest isolation story for HIPAA and enterprise security reviews, makes customer-managed keys and data residency per-cell settings, means one bug can't leak across customers, and keeps one artifact for both distributions. The cost is a fixed floor per customer, so the cell must stay cheap: scale-to-zero compute and a small Postgres. A pooled tier comes only with a free plan.

### 3.2 Components (per cell)

| Component | Responsibility |
|---|---|
| Edge | TLS, rate limits, request IDs |
| API (FastAPI) | REST, webhooks in and out, admin endpoints |
| MCP server | Same verbs as REST; user-scoped OAuth |
| Web app | Chat and admin console; console sections rendered by role |
| Workers | Connector sync, ACL sync, ingestion pipeline, compiler, indexer; durable job queue in Postgres first |
| Policy decision point | Library used by every read path: scope resolution → RLS context → post-check → egress check → audit |
| Model gateway | Provider adapters, quotas, budgets, retries, redaction, logging |
| Postgres | Control plane, metadata, chunks, embeddings, jobs, audit |
| Object store | Raw files and bronze OKF, encrypted with per-workspace keys |
| OpenFGA | Relationship store for roles and mirrored ACLs |
| Secrets backend | OpenBao (self-hosted default) or a cloud secret manager |
| Git (customer-owned) | Silver and gold OKF bundles |

### 3.3 Trust boundaries

| ID | Boundary | Primary controls |
|---|---|---|
| TB1 | Clients ↔ edge | OIDC tokens, OAuth for MCP (audience-bound), rate limits |
| TB2 | Cell ↔ customer IdP | OIDC now; SAML through a broker and SCIM later |

## 4. Tenancy, scope, and discoverability

- **Org** = company = cell. There is one org per cell in v1, but the schema supports more.
- **Workspace** = team. A workspace owns its connections, its bundle repo, its model registrations, an optional embedding override, and its policies.
- **Documents are stored once per org**, keyed by source identity, and linked into every workspace whose connection reaches them (`workspace_documents`).
- **Discoverability** is set per workspace:
  - `org` (default): included in org-wide scope.
  - `private`: visible to members only, never in org-wide scope for non-members.
- **Scope resolution:** a request's scope is either a list of workspaces or `org`.
  - `org` = every `org` workspace plus the private workspaces the caller belongs to.
  - Targeting a private workspace you aren't in returns 404, not 403, so its existence isn't disclosed.
- **Answers always carry the same note,** "Limited to sources you can access.", and never a count of hidden items.

## 5. Identity and authorization

### 5.1 Identity

- **SSO:** OIDC in v1 (Okta, Entra ID, Google, Keycloak). SAML through a broker in M6 or later.
- **Provisioning:** SCIM 2.0 in M6. Until then, users are created just-in-time from IdP claims and IdP groups.
- **Canonical principals:** `user:<id>`, `group:<id>`, `org:<slug>`.
- **Identity resolution:** `principal_aliases` maps source identities (GitHub login, Google account, Slack ID, Atlassian accountId) to canonical users. Resolution order:
  1. Verified IdP linkage (GitHub SAML or EMU identity, Google Workspace account).
  2. Verified email.
  3. Admin-confirmed manual mapping.

  Unresolved source principals are stored but grant nothing.
- **Principal validation:** principal strings are checked against a strict pattern before entering any RLS context. A comma or wildcard in an IdP group name must never expand access.

### 5.2 Roles

Roles are `owner` (org), `workspace admin`, `curator` (approves knowledge PRs, manages connections), `member` (reads), `auditor` (reads the audit log), and `service account` (machine client with explicit workspace grants). Roles also decide which console sections render.

### 5.3 Document permissions

- **Two copies, one truth.** Source ACLs are mirrored as relationships in OpenFGA (`container` and `document` types with parent inheritance). They are also denormalized onto each document, chunk, and embedding row as `acl_principals text[]`, holding the direct and inherited grants as principal IDs.
- **Read path:**
  1. Postgres RLS enforces `org_id` and `acl_principals && caller_principals` on every content table, so even a buggy query can't return unauthorized rows.
  2. The policy point then post-checks each returned document in OpenFGA.
  3. If the array allows a document but OpenFGA denies it (ACL drift), the document is dropped, an alert fires, and the drop is audited.
- **Group membership is expanded at query time,** through the caller's principals. Membership changes need no reindex; only grant changes do.
- **ACL freshness:** ACLs are updated from source webhooks and by periodic reconciliation, with `acl_synced_at` tracked per document. Confidential and restricted items whose ACL is older than the freshness SLO are withheld.
- **Live ACLs never go into Git.** Bundles carry classification and audience labels instead.

### 5.4 OpenFGA model (v1)

The JSON form in `authz/model.json` is what gets loaded; this is the readable form.

```
model
  schema 1.1
type user
type group
  relations
    define member: [user, group#member]
type org
  relations
    define admin: [user, group#member]
    define member: [user, group#member] or admin
type identity
  relations
    define owner: [user]
type workspace
  relations
    define org: [org]
    define admin: [user, group#member] or admin from org
    define curator: [user, group#member] or admin
    define member: [user, group#member, org#member] or curator
    define auditor: [user, group#member] or admin from org
type container
  relations
    define parent: [container]
    define viewer: [user, group#member, org#member, identity#owner] or viewer from parent
type document
  relations
    define parent: [container]
    define viewer: [user, group#member, org#member, identity#owner] or viewer from parent
```

## 6. Knowledge model

### 6.1 Tiers

- **Bronze:** one OKF concept per source document, a faithful machine conversion. Stored in the platform (object store plus `concept_versions`), versioned by content hash, and linked to the exact source revision. Not in Git by default.
- **Silver:** hubs and entities that integrate many bronze concepts. The compiler proposes them as PRs and humans review them; a `verified` entry with a `human:` actor gives the human-reviewed trust tier. Stored in Git.
- **Gold:** audience-shaped products such as runbooks, onboarding guides, and glossaries. Stored in Git.

### 6.2 Bundle layout

- One repo per workspace, `<org>/<workspace>-knowledge`, holding silver and gold.
- One org commons repo, `<org>/commons-knowledge`, for org-wide audiences only.
- Each repo is an OKF bundle at its root, with `index.md` and `log.md` per OKF. The root `index.md` declares `okf_version` and the `x-kl` profile version.

### 6.3 OKF profile (`x-kl`)

Native OKF fields are used exactly as the spec defines them: `type`, `title`, `description`, `resource`, `tags`, `sources` (with `id`, `resource`, `title`, `author`, `last_modified`), `generated`, `verified`, `status`, and `stale_after`. Everything else lives under `x-kl`:

| Key | Meaning |
|---|---|
| `id` | Stable concept ID that survives file moves (OKF's own ID is the path) |
| `aliases` | Names used for exact entity lookup |
| `classification` | `public`, `internal`, `confidential`, or `restricted` |
| `audience` | `org`, `workspace/<slug>`, or `group/<id>`. Must be no wider than the narrowest source audience (CI-enforced) |
| `owners` | For example `team:payments` |
| `relations` | Typed edges: `owns`, `owned-by`, `depends-on`, `approves`, `derived-from`, `supersedes` |
| `derivation` | Compiler version, model, and prompt version |
| `superseded_by` | Set on deprecated concepts |

Silver concepts cite bronze with a pinned URL in `sources[].resource`: `https://<cell>/k/<workspace>/bronze/<concept-id>@<hash>`. It resolves with auth and pins the exact bronze version.

### 6.4 Progression (lineage you can see)

Every concept has a timeline built from `concept_events`:

> source changed → bronze version → compile proposed (PR) → review (approved or changes requested, and by whom) → merged (commit) → indexed (snapshot) → cited in answers → stale → deprecated or superseded

Where teams see it:

- **Concept page:** the timeline, with a diff at each step.
- **Workspace pipeline board:** counts per stage, the review queue, stale concepts, coverage gaps, and rejected proposals.
- **API:** `GET /v1/concepts/{id}/history`.
- **Export:** `kl export --workspace X --tier bronze` emits a valid OKF bundle at any time.
- **Bronze Git mirror (optional):** `bronze_git_mirror: true` per workspace. It is refused when the workspace holds confidential or restricted content, or when the org is in HIPAA mode.

### 6.5 Corpus manifest

Every answer returns `{bundles: {<repo>: <sha>}, bronze_snapshot, index_snapshot, embedding_models}`. The same question with the same manifest produces the same retrieval set, and it can be replayed from the audit log.

### 6.6 Deletion

- **Source document deleted:** the platform writes a tombstone and purges the chunks, embeddings, and bronze versions. Silver and gold concepts that cite it are flagged, and CI opens a PR to remove or re-source the claim.
- **Regulatory delete of a workspace:** destroy the workspace's data key (crypto-shredding the object store and encrypted columns), drop its rows, and archive its repo per the customer's instruction.
- **Person-level erasure (GDPR):** find the person's identifiers across chunks and concepts (Presidio plus the identity table) and propose redactions. The source system remains the authority.

## 7. Ingestion

**Connector contract (Python `Protocol`):** `kind`, `test`, `discover`, `sync(cursor)` returning changes (upserts and tombstones), `fetch`, `acl`, `on_event`.

**Connector rules:**

- Use app and service identities only: a GitHub App installed on specific repos, Google service accounts on specific shared drives, Slack apps in specific channels. Never personal tokens for background sync.
- Sync only the containers the team selected.
- Give each connection its own ingest identity.
- Verify webhooks (HMAC).
- Rate limits and backoff live in the framework, not in each connector.

**Pipeline stages:**

1. **Acquire:** delta by content hash.
2. **Parse and OCR:** Docling by default; Document AI and Textract as adapters.
3. **Normalize:** Unicode NFKC, boilerplate removal, language detection, dedup.
4. **Classify and redact:** Presidio by default; Cloud DLP as an adapter.
5. **Stamp the envelope:** provenance, ACL snapshot reference, classification, lifecycle, derivation.
6. **Split into two paths:**
   - **Index:** structure-aware chunking (including code via tree-sitter), contextual chunk headers, embeddings using each workspace's model, and full-text search.
   - **Curate:** bronze OKF conversion, then the compiler.

## 8. Retrieval and answering

- **Router:** classifies the question's shape and picks strategies.
  - v1 strategies: (1) OKF entity and alias lookup, (2) hybrid search (full-text plus vector, fused with reciprocal rank fusion), (3) coverage-or-decline (score floor plus coverage map).
  - v2 strategies: graph traversal, version and as-of queries, metadata filters, attested computations.
- **Org-scope flow:**
  1. Retrieve within each workspace.
  2. Fuse with RRF across workspaces and retrieval channels.
  3. Rerank.
  4. Policy gate.
  5. Build the context.
  6. Send it through the model gateway.
- **Per-workspace embeddings:**
  - One `embedding_models` row per org default or workspace override.
  - Embeddings are stored per model, with a partial HNSW index per model.
  - The query is embedded once per distinct model in scope. Rank fusion means scores from different models never need to be compared.
  - Switching models is a blue/green re-embed (`building` → `active` → `retired`).
- **Synthesis model:** the caller picks from the models available to them through their workspace's registry. The egress check runs against that model for every chunk.

## 9. Models

**Registry (per workspace).** Each entry records:

- `provider`: one of `openai_compatible`, `anthropic`, `vertex`, `bedrock`, `azure_openai`
- `model` and `base_url`
- `credential_ref` (a reference, never the key)
- `allowed_classifications`
- flags: `baa_covered`, `zero_retention`

Registration runs a probe call and records capabilities. Workload identity or service-account impersonation is preferred over static keys: Vertex through ADC or workload identity federation, Bedrock through an IAM role.

**Gateway.** Handles quotas, budgets, retries and fallbacks, token and cost attribution, redacted logs, and injection screening of retrieved context.

**Egress policy.** Each piece of content's classification is matched against each model's `allowed_classifications`. In org-level HIPAA mode, PHI-tagged and restricted content may go only to `baa_covered` endpoints. Embedding calls obey the same rule.

**Defaults.** In the GCP reference deployment, Vertex AI is the default embedding provider and the reference generation provider.

## 10. Interfaces

**REST (OpenAPI 3.1):**

- `GET /v1/search`
- `POST /v1/ask`
- `GET /v1/concepts/{id}` (optionally `?at=<sha>`)
- `GET /v1/concepts/{id}/history`
- Admin APIs for workspaces, connections, models, policies, and audit
- Webhooks out: `bundle.merged`, `sync.completed`, `acl.changed`
- Webhooks in: GitHub App events

**MCP:**

- Tools: `search`, `ask`, `get_concept`.
- Resources: `kl://<workspace>/<concept-id>`.
- Auth follows the MCP authorization spec. The cell is the resource server; the authorization server brokers to the customer IdP (implementation chosen in M5).
- Read-only in v1. A later `propose_edit` tool opens a PR, never a direct commit.

**CLI and GitHub Action (knowledge CI):** authenticate to the cell with GitHub Actions OIDC, so no keys are stored in CI.

## 12. Security and compliance

### 12.1 Controls built into the product

- **Identity and access:** SSO, RBAC plus relationship-based document permissions, and Postgres RLS on all content.
- **Encryption:** TLS in transit, encryption at rest, per-workspace data keys, customer-managed keys per SaaS cell (later).
- **Secrets:** references only; values in the secrets backend.
- **Data flow:** egress policy, retention policies, and deletion propagation.
- **Audit:** append-only and recorded at retrieval-set level; hash-chained and SIEM-exported in M5.
- **Resilience:** encrypted backups with tested restores.
- **Supply chain:** SBOMs, signed images, SLSA provenance, dependency, secret, and container scanning, and GitHub Actions pinned by SHA.
- **LLM threats:** OWASP LLM Top 10 mitigations. Retrieved text is treated as untrusted data, external images and links are never auto-rendered, and tools are read-only by default.
- **Testing and observability:** the permission-leak suite gates releases; OpenTelemetry traces carry document IDs and never content.

### 12.2 Compliance approach

One control set, mapped to SOC 2 Trust Services Criteria, the HIPAA Security Rule, GDPR Articles 25 and 32, and ISO 27001 Annex A. Engineering builds the controls; attestations follow customers.

1. **Now:** build the controls and collect evidence automatically (CI logs, PR reviews, access changes).
2. **First paid SaaS customer:** a compliance automation platform (Vanta, Drata, or Secureframe), written policies, and SOC 2 Type I.
3. **Then:**
   - SOC 2 Type II, after a multi-month observation window.
   - A HIPAA program: BAAs with customers and with every subprocessor that touches PHI (the cloud provider, plus any model endpoint we provide), and HIPAA mode in the product.
   - GDPR: a DPA, a public subprocessor list, EU-region cells, and tooling for data subject requests.
4. **On demand:** ISO 27001 and third-party pentest reports. HITRUST, FedRAMP, or PCI only if a customer funds them.

**Self-hosted:** publish a shared-responsibility matrix and a hardening guide. Customers inherit the product's controls and operate the rest.

**Solo founder:** controls that assume a team, such as separation of duties and peer review, need documented compensating controls (protected branches, signed releases, immutable audit, and later an external reviewer). The automation platform handles this documentation.

### 12.3 Threat model priorities

1. Prompt injection through ingested content.
2. ACL drift and staleness.
3. Confused deputy through MCP or shared API keys.
4. Cross-workspace leakage through derived content and caches.
5. Egress to unapproved models.
6. Supply chain compromise.
7. Operator access in the SaaS.

## 15. How we work

- The repo is the source of truth. Decisions that change an invariant or add a dependency get an ADR in `docs/adr/`.
- `CLAUDE.md` carries the invariants for Claude Code sessions.
- Permission paths are written test-first, and the leak suite gates releases.
- Keep PRs small. From M1, CI runs on every PR: lint, types, unit tests, and the Compose-based integration and leak suites.
